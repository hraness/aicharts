# Private local usage ledger

This crate persists canonical numeric usage, local source checkpoints, pending measurement candidates, and explicit sender custody. It opens its own selected state directory, never provider sources. It has no network, account sign-in, credential storage, or daemon API. Sender layouts can acknowledge exact terminal receipts supplied by an owned authenticated transport; parsing a receipt does not authenticate its issuer.

## Persistence choice

| Option | Atomicity and recovery | Decision |
| --- | --- | --- |
| Separate cursor and frame files | Requires a new journal, locking and recovery protocol across files. | Not selected. |
| One rewritten numeric snapshot | Atomic replacement is possible, but every admission rewrites all retained data and still needs writer/recovery coordination. | Not selected for the ledger. |
| Embedded SQLite with rollback journal | Measurements, source checkpoints and pending candidates commit in one transaction. | Selected for local state only. |

R2 remains the proposed durable server measurement store. This local choice does not provision Turso or add a website database. `rusqlite` and its bundled SQLite are pinned by Cargo.lock. SQLite's [atomic-commit](https://www.sqlite.org/atomiccommit.html) and [synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) guarantees depend on working filesystem locking and durable flushes; tests do not prove every filesystem or storage device honors them.

## Current contract

- `initialize` creates a new mode-0700 directory and mode-0600 `usage.sqlite3`, never adopting an existing directory. An interrupted initialization can leave that exact directory incomplete; it is not automatically reset or overwritten.
- `open` requires the existing private directory and regular single-link files, checks the database application ID, schema version, exact schema and keyed namespace fingerprint, and rebuilds the bounded numeric projection to detect inconsistent rows. It never silently migrates or repairs unknown state. SQLite can recover its own valid hot rollback journal.
- `initialize_with_identity` and `open_with_identity` accept an explicit `LedgerIdentity`. `Legacy(key)` retains the original fingerprint exactly; the old constructors delegate to it. `SplitKeys { checkpoint, occurrence, namespace_version: 1 }` binds both nonzero 32-byte keys to a separate fingerprint for a new ledger. A different role, key or version refuses opening. This changes no existing database, key or outbox and performs no schema migration. The binding does not authenticate an account or authorize uploading.
- All source snapshots in `commit_scans` or `commit_prefix_scans` share one IMMEDIATE transaction and compare the caller's expected ledger revision. Errors, conflicts, bounds and interrupted pre-commit work leave the previous checkpoint, measurements and outbox together. Concurrent writers either wait outside the API and retry, or receive a fixed busy/stale-revision error; no best-effort partial import is returned. `commit_scans` applies only to the original layouts 1 and 2; prefix layouts require the separate prefix-aware API even for an empty import.
- A source checkpoint consists of a 32-byte keyed local source ID plus numeric file identity, length and timestamps. The CLI derives that ID from provider and canonical path, but neither the path nor any source content is stored. Metadata reuse is an optimization, not tamper evidence. Changed files are fully reparsed; the checkpoint is not resumable parser state or a byte-tail cursor.
- A rescanned source must retain its observed occurrence IDs and preserve native file identity. Legacy and unbaselined sources cannot shrink. A source with a complete-prefix witness can shrink only its uncommitted suffix, as specified below. Compatible Claude streaming revisions may advance; contradictions, disappeared prior observations, completed-prefix truncation and replacement stop admission without deleting old measurements. Sources omitted from a command remain retained. Source migration, explicit deletion and legitimate decreasing corrections require a later reviewed contract.
- Supported copied occurrences deduplicate globally. Source-specific last observations remain available for regression checks. Global Claude measurements use the existing compatible monotonic merge; an older independent copy cannot replace a later observation.
- The outbox coalesces the latest local candidate per occurrence. Its local revision is not a remote upload sequence or finalized server event. `pending` is bounded and read-only; subsequent pages must name the same ledger revision and fail if it changed. Layouts 1 and 3 retain every measurement in the outbox. Sender layouts 2 and 4 can conditionally acknowledge an exact accepted candidate, as described below; this crate never transmits a queue entry.

Stored measurement frames are canonical single-usage v1 frames of exactly 136 bytes. Only the current imported, unknown-model, unknown-account/auth historical reader profile is admitted. Prompt and interval records, live evidence, actual account/plan ownership and pricing dimensions remain unsupported. Tokens are still self-reported observations, not billing or provider attestations.

## Complete-prefix checkpoints

The four exact schema layouts are:

| Layout | Original numeric tables | Sender custody | Complete-prefix witnesses |
| --- | --- | --- | --- |
| 1 | Yes | No | No |
| 2 | Yes | Yes | No |
| 3 | Yes | No | Yes |
| 4 | Yes | Yes | Yes |

`Ledger::migrate_complete_prefix(dir, &identity, expected_revision)` explicitly adds the prefix table, moving layout 1 to 3 or 2 to 4. It preserves the namespace fingerprint, every original and sender row, and the local revision. Existing layouts 3 and 4 return validated readback without mutation. The table has exactly one row per source: all three witness fields are initially NULL for a migrated source, or all are present for a completed witness. Missing, orphaned, partially NULL, or invalid rows fail validation. Migration does not fabricate a digest or establish integrity of source bytes that were never witnessed.

`CompletePrefix { profile: 1, bytes, mac }` records the byte length and 32-byte keyed MAC of a fully replayed, LF-terminated source prefix. `bytes` cannot exceed the observed file size or the 256 MiB source cap. Zero completed bytes and any 32-byte MAC are representable. `prefix_snapshot()` returns an owned `PrefixSnapshot` with the ledger revision and `SourceCheckpoint { stamp, prefix }` per source. On layouts 1 and 2 it exposes `None` without migrating. These MACs are private local integrity metadata; do not include them in status output, exports, or uploads.

`commit_prefix_scans(expected_revision, scans)` accepts a full numeric replay plus the exact previous witness and newly completed witness. The collector must independently verify the old keyed prefix against the current source before replaying it; the ledger never opens that source or verifies the MAC itself. A source lacking its first witness must retain all previously observed numeric history and the old physical length. Its first successful baseline increments the revision and `sources_updated`, even when metadata and counters are unchanged. It establishes the current prefix, not proof of previously unwitnessed bytes.

For a witnessed source, the previous witness must exactly match the stored tuple, native device and inode must remain unchanged, and the new completed length cannot decrease. Equal completed lengths require equal MACs and the exact prior per-source canonical frame set. The physical file can shrink to the previous completed length if its uncommitted suffix disappears; committed numeric history still cannot disappear or regress. A changed completed prefix permits only the existing compatible numeric history updates. Future parser or registry corrections that change frames for identical bytes need an explicit reviewed reindex or profile-version transition.

All selected witnesses, checkpoints, measurements, and pending candidates commit together. Omitted sources remain retained. An unchanged metadata checkpoint may be skipped by an explicitly chosen collector optimization, but such a skip is not tamper evidence. Prefix witnesses do not implement append-resumable parser state, authenticate provider usage, or protect against a malicious same-user database rewrite or rollback. Source reads, newline selection, and keyed hashing remain collector responsibilities.

## Explicit sender custody

`Ledger::migrate_sender_v2(dir, &identity, expected_revision, &binding)` explicitly enables sender custody, moving layout 1 to 2 or prefix layout 3 to 4. It requires `SplitKeys` and an explicit nonzero account ID, device ID, recovery generation, and namespace version 1. One transaction adds six sender tables and changes the schema version while preserving the existing namespace fingerprint, measurements, checkpoints, prefix witnesses, local revision, and pending queue. A retry with the same binding reads existing state; a different binding is rejected. Ordinary opens, collection, and inspection never migrate. Older binaries refuse unsupported layouts rather than removing their state.

`freeze_upload_batch(expected_revision, &occurrence_ids)` freezes one to 256 unique pending occurrences under a revision check. It normalizes their order, allocates contiguous per-device sequences, and durably stores the exact canonical batch plus each local measurement revision before returning bytes. Only one batch can be in flight. An identical retry returns the same batch; another selection cannot replace it. `inflight_batch()` returns an owned copy for restart or uncertain-response reconciliation. Sequence numbers are independent of local revisions, range from one through `2^53−1`, and never reset or wrap.

Expected server heads come only from each occurrence's retained accepted receipt, or zero when no accepted receipt exists. The API does not accept replacement heads from callers. A returned conflict head is information for explicit reconciliation, not permission to overwrite another device's correction.

`settle_upload_batch(&terminal_journal)` first validates the entire journal against the frozen batch: canonical framing, binding, contiguous range, batch and operation hashes, receipt order, outcomes, and common server revision and timestamp. A new terminal journal must advance the last account-journal revision and cannot regress its commit time. Retained accepted and reconciliation receipts cannot postdate that latest journal. Its transaction then handles all members together:

- Acceptance retains one canonical operation and receipt per occurrence and removes an outbox entry only when its ID, local revision, and exact frame still match the frozen member. A newer local correction stays queued.
- A predecessor conflict or retained deletion leaves every candidate queued and creates a durable reconciliation gate for the affected occurrence. New collection cannot clear that gate. Batch-aborted members remain eligible for a later unchanged submission.
- A device-revoked journal blocks further freezing for the bound device across restarts.
- A timeout, HTTP error, staging response, or malformed/mismatched journal leaves custody unresolved. No sequence range or candidate is silently discarded.

Accepted and rejected terminal settlement consume the exact frozen range, retain the latest complete batch/journal pair, clear its in-flight custody, and increment the ledger revision atomically. `last_settled_batch()` provides owned existing-only readback. An exact repeated settlement returns `AlreadySettled` without further mutation; an older receipt that is no longer the retained terminal journal is rejected. There is no automatic retry, rebase, gate removal, device replacement, sequence reset, or tombstone emitter.

`sender_status()` reports the immutable binding, allocated and settled sequences, in-flight count, accepted occurrence count, reconciliation count, and revocation gate. Enrollment's short pairing deadline is not a sender credential expiry. Credential lifetime and current remote authorization remain transport/server responsibilities; the ledger stores no polling secret, upload-secret preimage, browser token, or namespace key.

Sender layouts replace measurement/outbox equality with checked coverage: each current measurement has either its exact pending candidate or an exact accepted frame and local revision. An older acceptance may coexist with a newer pending correction. Complete numeric inventory remains available after acknowledgment. Receipt correspondence and local consistency do not provide cryptographic issuer authentication or protection against a malicious same-user writer.

## Read-only reindex inspection

`ReadOnlyLedger::open(dir, &identity)` validates any of the four supported layouts without migration, owns a bounded snapshot, and closes its SQLite connection before returning. `snapshot()` exposes the local revision and source stamps, `prefix_snapshot()` additionally exposes private local witnesses, `status()` exposes numeric totals and pending counts, and `inventory()` returns every retained occurrence's ID, revision and exact canonical 136-byte frame. Inventory reads the measurements table explicitly; its contract does not depend on the outbox containing the same records. The type has no commit, acknowledgment, reset or activation method and retains only the namespace fingerprint, not either key.

The inspector validates private paths, database and directory identity, schema, namespace, integrity and numeric relationships within one short read transaction. It opens SQLite read-only with the bundled POSIX-locking `unix-excl` VFS. Connection-local EXCLUSIVE locking is set before database access so a raced WAL header cannot create shared-memory sidecars; this is not a write transaction. Any existing journal, WAL or SHM entry, including an empty or linked entry, produces `ledger_recovery_required` without cleanup or recovery. An unsupported WAL-mode main file can instead produce the fixed `ledger_storage_failed` if SQLite refuses its lock before mode validation. Failed inspection preserves the files for an explicitly chosen writer/recovery path.

`ensure_unchanged()` reopens and revalidates the source using the original resolved path, file identities, timestamps, schema, namespace, integrity and revision. Ordinary changes fail with a fixed stale, busy, invalid-state, private-state or recovery error. The owned snapshot does not hold a lock while the caller rereads sources, and this final check does not grant atomic promotion authority: activating a shadow ledger still requires writer coordination. Reindex coverage must compare exact normalized occurrences under the old key; matching counts alone is insufficient, and unavailable history cannot be reconstructed from opaque stored IDs.

This inspection path is qualified only for local macOS/Linux filesystems that honor POSIX locking. It does not copy session logs, recover a hot journal, create a lockfile or sidecar, or disable locking through `immutable`/`nolock`. Reading may update filesystem access times. File identity and revision guards reject ordinary replacement and races, but do not establish a security boundary against a malicious same-user process or a transient change restored between observations.

## Limits and confinement

The ledger caps 2,048 sources, 100,000 global occurrences, 200,000 source-to-occurrence associations, 100,000 input measurements per admission and 256 records per pending page. Multiple copies count toward association/work limits. The SQLite main file is capped at 256 MiB with 4 KiB pages; rollback journal space is additional. Open-time integrity reconstruction reads bounded numeric state, so unchanged source scanning does not imply constant-time startup.

Sender custody allows at most 256 in-flight members, one current batch, and one retained terminal pair. An upload is at most 82,024 bytes and its journal at most 67,744 bytes. SQLite's per-value/row length limit is 262,144 bytes so the paired row fits. Accepted and reconciliation tables each retain at most one row per occurrence, capped at 100,000 each; repeated corrections replace acceptance rather than append lifetime receipt history. The database byte cap can be reached before every independent row cap is exhausted.

One continuously open sender handle can reuse a connection-local audit stamp after a successful operation. The stamp compares schema cookie, schema version, [external-write data version](https://www.sqlite.org/pragma.html#pragma_data_version), [same-connection row changes](https://www.sqlite.org/c3ref/total_changes.html), and local revision inside the acquired transaction. Exact schema and namespace checks always run. A missing or changed stamp rebuilds the full numeric and sender projection; an unchanged stamp checks at most 768 occurrence IDs from the selected, current and last batches, plus bounded control rows and global count limits. Sender writes preserve the unmodified source projection and allocate only fresh sequence ranges. Their touched rows are checked before commit, and only the stamp captured inside that transaction is published after success. Collection, errors and failed write transactions invalidate the stamp. Completed read-only transactions may retain their captured stamp.

This optimization applies only while reusing the same managed connection. It does not retain a 100,000-receipt memory cache, skip full writer-open or read-only inspection audits, or prove integrity against arbitrary raw-file rollback, counter bypass or malicious same-user writes. The first sender operation on a reopened handle performs another full audit. Closing and reopening for every upload therefore forfeits the intended batching benefit; transport should keep the handle open without holding a transaction across network waits.

Connections use DELETE rollback journaling, EXTRA synchronous mode, full fsync where supported, in-memory temporary storage and SQL/blob size limits. No dynamic source-derived SQL, free-form fields, debug body logging or raw SQLite error text is exposed. Namespace keys are not stored. Fixed errors never include paths, source bytes or SQL details.

Persistent storage is enabled only on Unix in this source version. The existing parent is canonicalized before initialization or opening, supporting ancestor aliases such as macOS `/tmp`; the final state directory and database still reject symlinks. Private directory/file permissions are checked, and extra schema objects are rejected. This is not a descriptor-rooted sandbox, protection against a same-user malicious process or ancestor replacement races, an encrypted store, or proof of Windows ACL behavior. Keep state and its key in private directories on a local filesystem; do not place it on a network share or synchronize a live SQLite file through a cloud folder.

## Verification

`cargo test --locked -p aicharts-ledger` uses fresh synthetic state, including failed and abruptly terminated transactions, exact legacy/split bindings, owned occurrence inventory, stale snapshots, busy writers, and byte/directory preservation when refusing hot journals and foreign WAL files. Prefix tests cover all four layouts, explicit baseline rows, witness/revision compare-and-swap, unchanged-prefix frame equality, suffix shrink bounds, and preservation of accepted, gated, revoked, and in-flight sender state. Sender tests cover additive migration, maximum-size batches and journals, restart/readback, conditional acknowledgment with newer corrections, terminal gates, corruption, and process death before migration, freeze, or settlement commit. `cargo test --locked -p aicharts-cli` covers the command boundary separately. `bun run check` remains the full repository gate. Source privacy, logical recovery, authenticated receipt custody, and live installation qualification are different claims; no real provider session is needed by these tests.

The explicitly ignored `sender_100k_cost_probe` seeds 100,000 generated numeric occurrences, including 99,000 accepted receipts, performs a full writer-open audit, and times three real 256-member freeze/settlement cycles. Run `cargo test --locked --release -p aicharts-ledger sender_100k_cost_probe -- --ignored --nocapture` through the repository's host scheduler for a comparable cost check. It reports setup, full-open, per-batch and database-size measurements separately; no provider logs, credentials, uploads or timing assertion are involved.
